# ADR-009：声誉计分规则集中为 ReputationRulebook，跨模块以领域事件驱动

**状态**：已接受（Sprint 3 / Lab 6）｜ **驱动特征**：可测试性、可演进性、跨模块边界清晰
**相关 ADR**：衔接 ADR-002（事务性发件箱）、ADR-004（只追加声誉账本）

## 背景
Lab 6（Sprint 3）需完成「投票、采纳、评论、标签、声誉计算」，且实验明确要求验证"身份认证模块通过领域事件影响声誉模块"。
若各模块自行改动声誉分：加分规则会分散、难以测试与审计，且破坏限界上下文边界——这与 ADR-001 的模块化边界设计相冲突。

## 决策
1. **规则集中**：所有加分规则收敛到 `co-reputation` 领域层的 `ReputationRulebook` 单一点，作为可单测的纯函数暴露：
   - `initialPoints`：新账户初始积分
   - `voteDelta`：回答收到投票的 ±N 分值
   - `applyDailyCap`：单日加分上限，防止刷分
   - `BadgePolicy.forAcceptedCount`：被采纳次数达到阈值 → 徽章
   - `AcademicTerm.termKey`：按学期结算的账期划分
   - `Bounty.open`：悬赏开启时的额度校验
   - `ReputationAccount.open`：声誉账户开户
2. **事件驱动**：QA / 身份等模块**不直接触碰声誉表**；在「提问、回答、被投票、被采纳、评论」等发生时发布领域事件（经 ADR-002 事务性发件箱保证可靠投递），声誉模块订阅后计分入账（写入 ADR-004 的只追加账本）。
3. **幂等**：账本唯一键 `(event_id, user_id, reason)`（ADR-004）保证事件重复投递只记一次，重放安全。

## 后果
- **正面**：加分规则单一来源，可单测、可审计；跨模块边界清晰（QA/身份 → 事件 → 声誉）；补全规则即让 CI 转绿。
- **负面**：一次动作增加一次事件投递与账本写入（衔接 ADR-004 已记录的写放大）；规则具体数值需后续依据访谈激励诉求调优。

## 被否决的替代方案
- **各模块自行 `UPDATE` 声誉**：规则分散、不可审计、破坏限界上下文边界。
- **声誉模块反向调用 QA 模块查业务表计分**：产生反向依赖，边界混乱。
- **无每日上限的无限累计**：易被刷分，违背访谈提炼的"可信度"诉求。

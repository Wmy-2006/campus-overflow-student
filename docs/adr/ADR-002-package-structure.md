# ADR-002：多模块工程与包结构（分模块决策）

> 状态：已接受
> 日期：2026-10（Lab4 / Sprint2）
> 上下文：Q&A 问答 · 后端工程骨架

## 背景

CampusOverflow 需要按 DDD 限界上下文做物理分离，同时满足课程对"多模块 Maven 工程、可测试、可演进"的要求。需要决定：工程拆成几个模块、每个模块内部如何分层、如何保证上下文间依赖干净。

## 决策

采用 **Maven 多模块 + 模块内六边形四层分包**：

### 模块划分（6 个）

| 模块 | 职责 |
| --- | --- |
| `co-bootstrap` | 唯一启动入口，装配全部模块、加载配置（application.yml） |
| `co-shared-kernel` | 共享内核：领域异常、Guard、Actor、事件基建、分页、审计 |
| `co-identity` | 身份与认证上下文（用户、课程、教师认证） |
| `co-qa` | 问答上下文（问题、回答、投票、评论、标签） |
| `co-reputation` | 声誉上下文（积分账本、徽章、悬赏） |
| `co-discovery` | 发现上下文（检索、推荐、通知） |

### 每个业务上下文内的四层分包

```
com.campusoverflow.<context>
├── api            # 发布语言：跨上下文契约（事件 record、对外 API 接口）
├── domain         # 纯 Java 领域层：聚合、值对象、仓储接口、领域事件
├── application    # 用例编排：命令/查询服务，依赖端口而非实现
├── infrastructure # 持久化与基础设施：JPA 映射、仓储适配器、Flyway 迁移
└── interfaces     # REST 接口层：Controller、参数校验、Actor 解析
```

## 后果

- **编译期即边界**：跨上下文只能通过 `api` 的发布语言依赖，杜绝包环与隐式耦合。
- **可测试性**：应用服务只依赖端口接口，单元测试用内存替身即可毫秒级完成，无需数据库。
- **单一启动点**：只由 `co-bootstrap` 装配，避免多个可运行入口。
- **代价**：跨模块重构需显式调整依赖，初学阶段对依赖方向要求更严格。

## 被否决的替代方案

1. **单模块 + 包目录划分**：失去编译期边界，上下文间易产生循环依赖，故否决。
2. **微服务拆分**：四人团队规模与课程周期无法承担分布式运维、事务与测试复杂度，故否决（保持模块化单体）。
